# Database architecture

## Stack

PostgreSQL 16 + Prisma 5. Schema source of truth: `packages/db/prisma/schema.prisma`.
The generated Prisma Client is written to `packages/db/generated/client`
(git-ignored, regenerated by `npm run db:generate`).

## Tables (Phase 1-2)

| Table               | Purpose                                                                 |
| ------------------- | ------------------------------------------------------------------------ |
| `users`              | Accounts, Argon2id password hash, `role` (USER/ADMIN).                  |
| `refresh_tokens`      | Hashed refresh tokens, rotation family, revocation. See `auth.md`.      |
| `documents`           | One row per document. `document_type`, `is_synthetic`, reserved `key_findings` JSON. |
| `document_pages`      | Reserved for per-page text (OCR/layout phase).                          |
| `document_sections`   | Reserved for structural sectioning.                                     |
| `document_clauses`    | Reserved for clause spans (clause classification phase).                |
| `entities`            | Reserved for entity spans (NER phase).                                  |
| `relations`           | Reserved for entity-to-entity relations (relation extraction phase).    |
| `risks`               | Reserved for flagged risk findings (risk engine phase).                 |
| `obligations`         | Reserved for extracted obligations.                                     |
| `embeddings`          | Reserved for vector embeddings (see pgvector note below).               |
| `processing_jobs`     | Reserved for async pipeline job tracking.                               |
| `audit_logs`          | Reserved for security/administrative audit trail.                       |

No phase-1-2 code writes to `document_pages`, `document_sections`,
`document_clauses`, `entities`, `relations`, `risks`, `obligations`,
`embeddings`, or `processing_jobs` — they exist only so later phases don't
need a breaking migration to start using them. `packages/db/tests/schema.test.ts`
exercises the shape of a few of these tables purely to prove the
`document_id` grouping and cascade-delete behavior work, not as a sign
those tables are "in use" yet.

## `document_type` constraint

`documents.document_type` is a native Postgres enum (`document_type`) with
exactly two values: `residential_rental` and `land_lease` (mapped from the
Prisma enum members `RESIDENTIAL_RENTAL` / `LAND_LEASE` via `@map`, so the
raw stored string matches the dataset's `manifest.jsonl` /
`*.labels.json` `document_type` field exactly). Any other value is
rejected by Postgres at the database level — this is verified in
`packages/db/tests/schema.test.ts` via a raw `INSERT` with an invalid
value, which is expected to throw.

Commercial leases and general contracts are out of scope for this
project and are not representable by this enum.

## `document_id` grouping columns (cross-validation requirement)

Every table that will eventually hold a per-document derived sample
(`document_pages`, `document_sections`, `document_clauses`, `entities`,
`relations`, `risks`, `obligations`, `embeddings`, `processing_jobs`)
carries a non-nullable `document_id` foreign key back to `documents`.
This is required so that a future evaluation script can group all
derived rows by source document and run `StratifiedGroupKFold` with
`group = document_id`, `stratification = document_type`, per
`evaluation_design.md`. No schema change should be needed to support
that later.

## pgvector (explicitly not enabled in this phase)

`embeddings.vector` is a nullable `Json` column in this phase — a plain
array of floats can be stored there once an embedding model is wired up
in a later phase, but no vector *search* is implemented or possible yet.

A future phase is expected to:

1. Add the `pgvector` Postgres extension via a migration
   (`CREATE EXTENSION IF NOT EXISTS vector;`).
2. Add a native `vector(N)` column (Prisma's `Unsupported("vector(N)")`
   type, since Prisma does not have first-class pgvector support as of
   this writing) alongside or replacing the JSON column.
3. Backfill/migrate any JSON-stored vectors into the native column.

No pgvector extension, column type, or client dependency is added in
Phase 1-2.

## Provenance fields

See `provenance.md` for the full design. In short: `document_clauses`,
`entities`, `relations`, `risks`, and `obligations` each carry both a
canonical text offset pair (`text_start`, `text_end`) and a nullable
visual/page provenance group (`page_number`, `bbox_x`, `bbox_y`,
`bbox_width`, `bbox_height`), plus `confidence`, `model_name`,
`model_version`. None of these are populated yet.

## `key_findings`

`documents.key_findings` is a nullable `Json` column reserved for the
top-level findings digest described in `schema.md`. Not populated in
this phase.
