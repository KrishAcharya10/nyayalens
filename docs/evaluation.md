## How to read these numbers

- **Synthetic only.** Every document was produced by the project's own generator (`research/generator/v3`). The extraction rules were written by the same project, against the same generator's surface forms. These numbers show the system handles the forms it was built for; they are **not** an estimate of accuracy on real-world documents.

- **Development data vs. final data.** Rules were developed and tuned against a seed-2026 dataset (whose test split was inspected while tuning) and a seed-99 development dataset. The final numbers below are on a freshly generated dataset (see the seed above) that was not inspected before this run. It still comes from the same templates and value pools, so it is a check against overfitting to specific documents, not to the generator.

- **Held-out templates.** Test documents use held-out clause templates on 50% of draws; the generator's validator reports 0 template leakage and 0 train/test near-duplicates (MinHash, Jaccard >= 0.8).

- **No trained model.** Every number is from the rule-based pipeline (`model_source = RULE_BASED`). No model was trained or fine-tuned in Phase 8.

- **Same code as production.** The harness calls the same functions the upload pipeline calls (NER, clause classification, semantic analysis, consistency, risk checks, domain detection, structured QA), in memory, on each document's raw text. OCR is not exercised.

## Known limitations

- Real-document performance is unmeasured. Indian agreements vary far more in layout, wording, OCR quality and language mixing than any generator.

- Clause classification is heading-based: a clause with an unusual heading is missed, which then also produces a false MISSING_CLAUSE finding.

- Obligation extraction is sentence-level and pattern-based; obligations spread over several sentences, or stated without a modal verb, are missed.

- Legal reference metadata is UNVERIFIED and is never presented as legal applicability (docs/legal_reference_policy.md).
